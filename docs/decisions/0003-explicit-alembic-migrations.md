# ADR 0003: Explicit Alembic migrations instead of `create_all()`

- Status: Accepted
- Date: 2026-08-01

## Context

An ORM model describes what application code expects now. A live database has
history: columns may need backfills, constraints may need staged rollout, and
deployments may run different application versions briefly. Calling
`metadata.create_all()` creates missing objects but is not an ordered,
reviewable record of how one schema becomes another. Changing an ORM class also
does not migrate an existing database.

## Decision

Use Alembic for explicit, reviewed, ordered schema migrations. Operators or
deployment automation run `alembic upgrade head` as a separate release step;
the API does not silently migrate on every process start.

Stage 1 configures the migration environment but intentionally creates no
empty baseline revision. Stage 2's first meaningful domain model should create
the first meaningful revision.

## Serious alternatives

### SQLAlchemy `metadata.create_all()`

This is convenient for prototypes and disposable test databases. It does not
represent destructive or data-moving changes, has no ordered history, and can
make application startup race when several instances start together. It is not
the production migration strategy.

### Hand-written SQL files

Plain SQL gives maximum control and is sometimes the right tool inside an
Alembic revision. On its own, it needs a home-grown version table, ordering
rules, invocation tooling, and rollback policy. Alembic already supplies that
framework while still allowing explicit SQL.

### Automatic migration at API startup

This looks convenient but couples serving traffic to a privileged, potentially
slow schema operation. Multiple replicas can contend, and a failed migration
can cause a restart loop. A separate explicit step is easier to observe and
control.

## Consequences

- Every schema change requires a reviewed revision and migration test.
- Autogenerated revisions are drafts; a human must inspect types, constraints,
  data movement, and downgrade behavior.
- Deployments must run the migration step before code that requires the new
  schema receives traffic.
- The lack of a Stage 1 revision is intentional, not missing work.
